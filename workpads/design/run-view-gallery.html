argus · run-view merge gallery

Six ways to MERGE Progress + Execution into one click-to-expand run view (Plan stays separate), rendered over one sample run (modal-rust-plan-research · fan-out + 1 failed) using the harness grammar: dashed = pending · solid card = active · accent diamond = decision · dashed-accent = loop. See workpads/design/run-view-merge-plan.md for the converged decision.

Lane-expand

best for: one run, two zooms — the painted plan DAG that drills into real instances without leaving the view. Stance: ONE run view (Plan stays a separate template view; Progress + Execution collapse into this). Default is the collapsed plan shape — pending steps are dashed ghosts, done/running steps are solid cards. A fanned step shows a ▾ caret + ×N chip and expands inline into its instance cards (failed = red, upcoming = dashed) — "click to expand, not a separate tab." Handles adversarial-verification as an accent VERIFY diamond gate that the fan-in passes through; renders loop-until-done as a dashed accent back-edge off the gate, and tournament by letting each bracket round be its own expandable fan-out lane (the eliminated branch's instances stay red/dimmed in the drawer).

Accordion / phase outline

best for: many-agent runs & vertical scanning — ONE run view: each phase is an outline row showing a status rollup (×N, mini-bar) that expands downward to its instance cards. Plan stays a separate view; here Progress and Execution fold into a single click-to-expand outline (aggregate row = old Progress, expanded cards = old Execution). Dashed-vs-solid carries plan-vs-run: a not-yet-run phase is a dashed ghost row that can't expand; spawned instances are solid cards, un-spawned ones dashed ghost tiles. Hardest patterns: adversarial-verification renders as the accent gate badge on the REVIEW row (turns red when a reviewer trips it); loop-until-done is a dashed accent return row under the gate; a tournament nests as round sub-rows inside one phase (each round an inner accordion).

Semantic zoom

best for: one fluid run view with no tabs — the SAME canvas at every zoom: dragging the detail slider morphs the run between the plan shape (zoomed out: fan-outs are single ×N nodes, dashed where pending) and the per-instance reality (zoomed in: each fan-out materializes into individual agent cards in place). Stance: ONE run view — Progress and Execution were the same run at two zooms, so they collapse into a slider; Plan stays a separate run-free template. Loop-until-done reads as a dashed-accent back-edge off the verify diamond (re-runs land as new instances inside the same fan, the LOD just deepens); a tournament is the same gate cascaded — each bracket round is one fan-out feeding the next, so deeper zoom reveals more rounds rather than a new layout. The frame below is held at mid-zoom: RESEARCH has bloomed into its 5 solid instance cards (a realized fan-out) while SYNTHESIZE is still a dashed ghost — the article's "solid card amid dashed placeholders," in one view.

Split / master-detail

best for: the everyday "what ran & what happened" loop — the painted plan DAG up top is the map, and selecting any step opens a detail drawer of its actual instance cards below. ONE run view with a detail region: it folds the old Execution tab into an in-context drawer ("click to expand, not a diff tab"), keeping the template-vs-instances distinction as map-vs-detail rather than two redundant canvases. Hardest patterns: fan-out-and-synthesize is native (an aggregate node up top, its N instances in the drawer). A loop-until-done reads as a verify diamond with a dashed accent back-edge in the DAG; selecting the loop step lists each iteration as a dated instance row in the drawer (re-runs stack chronologically). A tournament selects a round to reveal that round's matchups as instances, with eliminated branches greyed — the bracket stays in the map, the per-match detail drops below.

Badge-Peek

best for: a dense, stable run overview you drill on demand. The plan DAG stays compact — a fanned step never grows; it wears a status-count badge cluster (●3 ◌2 ✕1) and the verify step is an accent diamond. Click/hover a step → an ephemeral peek lists its instances (label · status · duration); each row opens the DetailPanel. Stance: ONE run view (plan-shaped) + a throwaway popover — the badge answers "how many / which states" at a glance, the peek answers "which ones," the panel answers "everything about one." Plan stays its own separate view. Loop-until-done: the back-edge re-enters the same compact node; its badge just re-counts per pass (×pass shown in the peek footer) — the node never multiplies. Tournament: each round is one fanned step whose badge reads survivors (e.g. ●4 ✕4); the peek lists winners↑ / eliminated↓ without widening the bracket. Shown mid-run: REVIEW is the live decision gate (correctness+security ◌ running, feasibility ✕ failed) with its peek open, so SYNTHESIZE is still a dashed ghost.

Run — one view, density-controlled (two-views-kept)

best for: collapsing Progress + Execution into one Run view without inventing a third tab. The 1-vs-2 stance: keep exactly TWO views — Plan (the run-free template) and Run — but make Run a single canvas with an internal density segment (Shape ↔ Mid ↔ Instances) instead of separate Progress/Execution tabs; Progress was just Run at min density, Execution was Run at max density. Loop & tournament: a loop-until-done back-edge is a dashed accent line off the verify diamond that re-enters the prior phase band — it draws once and survives every density level (density changes card detail, not topology); a tournament's bracket elimination is the same fan group with losing instances dimmed/struck and only the winner's merge edge feeding forward. Verdict (argued below): one Run + a density control beats a single fixed Run view — but it does not justify a third top-level tab, which is exactly why Progress/Execution should die.
